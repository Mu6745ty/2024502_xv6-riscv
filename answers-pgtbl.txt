Part 1: Inspect a user-process page table
==========================================

A page table entry (PTE) tells the CPU where a virtual page is in
physical memory and what the process is allowed to do with it.

Permission bits: V = valid, R = read, W = write, X = execute,
U = user can access, A = accessed, D = dirty (page was written to).

va 0x0, perm 0x5B (V R X U A)
  This is program text (the code). The user can read and execute it,
  but cannot write to it. The A bit is set because the CPU has
  already run instructions from this page.

va 0x1000, perm 0x1B (V R X U)
  This is more program text. The program is bigger than one page.
  The A bit is not set because this page has not been used yet.

va 0x2000, perm 0x17 (V R W U)
  This is the data page (global variables). The user can read and
  write it, but cannot execute it.

va 0x3000, perm 0x7 (V R W, no U)
  This is the guard page below the stack. The U bit is off, so user
  code cannot use it. If the stack grows too far, the program touches
  this page and gets a fault instead of silently damaging other data.

va 0x4000, perm 0xD7 (V R W U A D)
  This is the user stack. The user can read and write it. The A and D
  bits are set because the program has already used and changed it.

va 0x5000 to 0x9000, pte 0x0
  These pages are not mapped. Nothing is stored there (the heap has
  not grown yet). Using them would cause a page fault.

va 0x3FFFFF6000 to 0x3FFFFFD000, pte 0x0
  These pages are also not mapped. They are empty space below the
  trapframe.

va 0x3FFFFFE000, perm 0xC7 (V R W A D, no U)
  This is the trapframe. The kernel saves the user registers here when
  a trap happens. The U bit is off, so only the kernel can use it.

va 0x3FFFFFF000, perm 0x4B (V R X A, no U)
  This is the trampoline. It holds the code that switches between user
  mode and kernel mode. The U bit is off, so user code cannot use this
  page directly. It is mapped at the top of every address space.

Note: The physical addresses (pa) are not in order. xv6 does not put
consecutive virtual pages next to each other in physical memory.

Part 2: vmprint
===============

vmprint walks the page table tree and prints every valid entry. The
top and middle entries point to lower tables. Only the bottom entries
(leaf pages) point to real memory, and these show the permissions.

Leaf pages in the output:

va 0x0 (RXU) and va 0x1000 (RXU)
  Program text (code). The user can read and execute it but cannot
  write it. These are the same pages as va 0x0 and 0x1000 in
  print_pgtbl, with the same physical addresses.

va 0x2000 (RWU)
  Data page. The user can read and write it, but cannot execute it.

va 0x3000 (RW, no U)
  Guard page below the stack. User code cannot access it, so a stack
  overflow causes a fault instead of damaging other memory.

va 0x4000 (RWU)
  User stack. The user can read and write it.

va 0x3fffffe000 (RW, no U)
  Trapframe. The kernel saves the user registers here during a trap.
  Only the kernel can use it.

va 0x3ffffff000 (RX, no U)
  Trampoline. This is the code that switches between user mode and
  kernel mode. It is executable but not usable directly by the user.

How it relates to print_pgtbl: both show the same pages with the same
physical addresses. print_pgtbl showed the raw permission number (for
example 0x5B), while vmprint shows letters (RXU) and skips the empty
pages. vmprint does not print the A and D bits.

The top level has only two entries (0 and 255) because the process
uses only the low addresses (code, data, stack) and the very top
(trapframe and trampoline). Everything in between is not mapped, so
no lower tables are needed for it.

Part 4: Speed up getpid
=======================

I allocate one page for each process and map it at USYSCALL with
PTE_R and PTE_U (no PTE_W). The kernel stores the pid at the start of
the page. User code can read it directly, so ugetpid() needs no trap
into the kernel.

The page is allocated in allocproc, mapped in proc_pagetable,
unmapped in proc_freepagetable and freed in freeproc, the same way as
the trapframe.

Which other system calls could use this page?
  - uptime(): the kernel could write the current tick count into a
    shared read-only page each time the timer interrupt fires. The
    user would just read it.
  - sbrk(0): the kernel could keep the process size (p->sz) in the
    shared page and update it whenever the size changes. Asking for the
    current size would then only need a read.
These calls only return kernel data and change nothing, so reading a
shared read-only value is enough. The kernel must keep the value up to
date, and the page must never be writable by the user.

Part 5: Superpages
==================

I made a copy of mappages called kmappages that only kvmmap uses. It
uses a 2 MB superpage (one level-1 leaf PTE) when the virtual and
physical addresses are 2 MB-aligned and at least 2 MB is left.
Otherwise it maps normal 4 KB pages. User page tables still use the
original mappages, so user processes only get 4 KB pages.

Superpage PTEs used: 95
  - PLIC region: 32 (64 MB / 2 MB)
  - kernel data / RAM region:  63 (from 0x80200000 to PHYSTOP,
    126 MB / 2 MB)


Bottom-level pages saved: 95 x 512 = 48,640.
Each superpage replaces 512 bottom-level pages, so we also need
fewer page-table pages and fewer TLB entries.
